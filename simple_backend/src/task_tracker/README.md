## Хранение состояния и минусы in-memory подхода

**Хранение состояния** — это сохранение данных приложения между запросами и перезапусками.  
В первом варианте проекта задачи хранились в оперативной памяти Python-процесса (`dict[int, Task]`).

### Минусы in-memory хранения
1. **Потеря данных при перезапуске** – рестарт сервера/краш = список задач обнуляется.
2. **Нет шаринга между процессами/инстансами** – каждый воркер держит свой список; в проде с несколькими инстансами данные расходятся.
3. **Невозможно горизонтально масштабировать** – без внешнего общего хранилища инстансы не согласованы.
4. **Нельзя сделать бэкапы и восстановление** – память не предназначена для долговременного хранения.
5. **Трудно гарантировать целостность** – при одновременных запросах возможны гонки (race conditions) и потеря обновлений.
6. **Утечки памяти** – долгоживущий процесс с растущим списком может съесть RAM.
7. **Нет истории/аудита** – нельзя восстановить кто/когда что изменил.
8. **Сложная эксплуатация** – деплой/rollback/аварии приводят к потере данных, а локальная разработка не совпадает с продом.

## Переход от хранения задач в оперативной памяти к файлу проекта

### 1. Что улучшилось после перехода
- ✅ Данные переживают перезапуск приложения — список задач сохраняется в `tasks.json`.
- ✅ Единая точка правды — один файл для всех эндпоинтов вместо глобального словаря в памяти.
- ✅ Проще отлаживать — можно открыть файл и увидеть текущее состояние.
- ✅ Возможны бэкапы — файл можно коммитить/копировать/архивировать.

### 2. Избавились ли мы полностью от «хранения состояния»
- ❌ Нет, не полностью.  
  Состояние по-прежнему есть — теперь оно хранится на диске (в файле), а не в RAM.  
  ➡️ Зато оно стало **персистентным** (persisted) и не пропадает при рестарте.

### 3. Где ещё можно хранить задачи и плюсы/минусы

#### Файл (JSON / CSV / YAML)
- ➕ Просто стартовать, читать глазами, без инсталляции БД.  
- ➖ Неудобно при больших объёмах, нет транзакций, возможны гонки записи.

#### SQLite (встроенная БД, файл `.db`)
- ➕ Транзакции, индексы, запросы SQL, всё в одном файле.  
- ➖ Всё ещё локально, нужно продумать бэкап/совместный доступ.

#### PostgreSQL / MySQL
- ➕ Надёжно, транзакции, индексы, репликация, бэкапы.  
- ➖ Нужна инфраструктура и развёртывание.

#### NoSQL (MongoDB, DynamoDB)
- ➕ Гибкие схемы, масштабирование.  
- ➖ Другая модель данных/запросов.

#### Облачные JSON-хранилища (jsonbin.io / mockapi.io / GitHub Gist через API)
- ➕ Быстро и без инсталляций, удобно для pet-проектов.  
- ➖ Зависимость от внешнего сервиса, ограничения тарифов.

### Состояние гонки (race conditions)

После переноса данных в jsonbin бэкенд стал stateless, но осталась проблема гонок при одновременных изменениях:

- **Потерянные обновления** — два клиента по очереди сохраняют разные изменения одной задачи, последнее перетирает первое.
- **Дубликаты/конфликты id** — два параллельных создания задач используют один и тот же `next_id`.
- **Непредсказуемые результаты** — чтение делается из «устаревшего» состояния.

#### Варианты решения
1. **Оптимистическая блокировка (version/ETag + If-Match)**  
   Хранить в документе поле `version` (или использовать ETag сервиса).  
   На запись отправлять условие: «сохраняй, только если версия = X», иначе вернуть 409 Conflict.
2. **Пессимистическая блокировка**  
   Лочить ресурс на время записи (подходит для БД/файла с блокировками; в jsonbin недоступно).
3. **Сingle-writer**  
   Все записи идут через одну очередь/воркер, который последовательно пишет во внешнее хранилище.
4. **Перейти на БД с транзакциями**  
   PostgreSQL/SQLite решают проблему на уровне ACID и дают надёжные механизмы конкуренции.
